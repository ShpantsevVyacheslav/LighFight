# LighFight — единый бэклог

Обновлён: **15 октября 2026**. Текущая телефонная версия: **сборка 101** в LighChat / Game Hub.

Цель ближайшего этапа: стабильный бой на iPhone с удобным управлением, корректными попаданиями и качественными персонажами. Следующее направление разработки задаст владелец после теста. Этот документ не запускает новые работы автоматически.

Это основной реестр текущих задач. Старые журналы сохраняются как история, но их отметки «реализовано» и зелёные локальные тесты не отменяют дефекты, найденные владельцем на телефоне.

## Как читать статусы

| Статус | Значение |
|---|---|
| Запланировано | Требование записано; готового решения ещё нет |
| В работе | Задача начата, но код/контент ещё не готов к приёмке; возможны только диагностика или черновик |
| Готов код | Реализация и доступные локальные проверки выполнены; пользовательская приёмка остаётся отдельной |
| Протестировано пользователем — пройдено | Владелец явно подтвердил успешный результат именно этой задачи |
| Протестировано пользователем — дефект | Владелец проверил и сообщил проблему; задача остаётся открытой |

В таблицах **разработка** и **пользовательский тест** разделены: у уже существующего кода может быть провален тест. «В работе» не означает, что сейчас запущен фоновый процесс. Для дизайна и 3D-контента готовность означает завершённый проверенный результат, а не только наличие скрипта или генерации.

Пока нет отдельного положительного подтверждения владельца по конкретным исправлениям сборки 101. Отсутствие замечания не считается успешным тестом.

## Приоритеты

- **P0 — критично:** мешает продолжительному использованию игры.
- **P1 — ближайший основной этап:** качество боя, управления и персонажей.
- **P2 — следующий этап:** полная переработка интерфейсов, индивидуальность бойцов и окружение.
- **P3 — развитие:** турнир, история и свободный мир после стабилизации основного боя.

Приоритет показывает важность, а не обязательный последовательный порядок. Например, дизайн можно готовить параллельно диагностике, но реализацию новых интерфейсов начинать после принятия дизайна.

Это требования к проектированию, **не утверждение о готовой раскладке**:

| Жест | Ожидаемое действие |
|---|---|
| Тап слева | Удар левой рукой |
| Тап справа | Удар правой рукой |
| Диагональ вниз | Лоукик |
| Диагональ вверх | Удар в голову |
| Вертикальный свайп вверх из верхней части | Апперкот |
| Прямой свайп из нижней части | Прямой удар ногой; направление определить в дизайне |

Полная таблица должна дополнить эти примеры всеми доступными ударами и устранить пересечения с движением/интерфейсом. Не менять смысл примеров молча.

### Уточнение проверки трапеций и танцев

- Последний дефект владельца относится к контуру **от шеи к плечу**, особенно при поднятой руке. Исправление наружного края рукава само по себе этот дефект не закрывает.
- Выявлены две независимые проблемы: скачки при Humanoid-переносе исходного танца и остаточная деформация ключичной области. Прямое чтение оригинальных Generic-кривых устранило обнаруженные скачки в локальном пилоте Моряка; провал у воротника ещё виден, поэтому пилот не принят и не распространён на остальных.
